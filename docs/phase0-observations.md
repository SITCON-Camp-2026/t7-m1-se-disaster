
# Phase 0 Observations

## 我們做出了什麼？

- 建立了前端工作台（`Phase0Workbench`）與原始資訊面板（`Phase0RawInfoPanel`）。
- 實作了一組 heuristics（`phase0-heuristics.ts`）用來自動判斷報告的關鍵欄位。
- 準備了原始資料夾 `src/fixtures/phase-0/messy-reports.json` 作為測試與展示用。
- 撰寫並通過單元測試，確保基礎資料契約與篩選邏輯可運作。

## 哪些資料讓 agent 很容易整理？

- 結構化欄位（例如 `site_id`、`timestamp`、`status`）可直接映射到資料模型。
- 固定格式的數值欄位（如確切數量、GPS 座標）在標準化後能可靠處理。

## 哪些資料讓 agent 亂補或誤判？

- 自由文字描述（地點描述、口語化地名）會造成地點歧義。
- 含糊的數字（「多數」「幾人」）會被誤解為精確數值。
- 不同來源互相矛盾但缺乏時間戳記，導致 agent 無法判斷哪個是較新的資訊。

## 哪些資訊不能直接變成任務？

- 推測性需求（例如「可能需要食物」）未明確受災範圍與優先順序，不能直接轉成任務。
- 二手描述或未具名來源的狀況（例如社群轉述）需先驗證來源可信度。

## 哪些資訊的操作者不是當事人？

- 記錄中有媒體或轉發者（aggregator）標記，內容並非原始回報者。
- 社群貼文或記者報導常是二次資訊，可能缺乏現場細節或精確位置。

## 我們剛剛偷偷假設了什麼？

- 假設 `site_id` 可以直接對映到 `sites.json` 中的站點（但有時描述非標準化）。
- 假設時間戳的時區一致或可比，實際上可能需要正規化處理。

## 如果要讓這個工具變可靠，下一步需要什麼？

- 建立一個最小欄位規格（schema），明確哪些欄位是必填與其型別。
- 新增「人工確認（verification）」流程：在 UI 上能標註 `verified` / `unverified` 與註解理由。
- 提供地點正規化工具（地名到 site_id 的手動/半自動映射）並記錄映射理由。
- 為自由文字欄位建立常見實體抽取與模糊比對，降低歧義。

## 我們需要更清楚資料格式的地方

- `location` 欄位：建議拆成 `site_id`（可選）、`address_text`、`lat`/`lon`。
- `counts` 欄位：明確欄位命名（`injured_count`、`fatal_count`、`missing_count`），並允許 `approximate: boolean` 標記。
- `source` 欄位：需要 `source_type`（official/media/volunteer）、`author`、`verified` 標記。

## 我們需要人工確認的地方

- 確認事件位置（`site_id` 或精確地址）是否對應正確站點。
- 核實人數與受災程度（是否為近場觀察者或二手資訊）。
- 確認報告時間與時區，解決時間序衝突。
- 檢查有無重複回報（deduplicate）及合併策略。
